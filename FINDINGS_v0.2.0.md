# Findings — v0.2.0 battery on Claude Opus 4.7, Sonnet 4.6, Haiku 4.5

Run window: results captured 2026-05-19 to 2026-05-27 via `scripts/batch-v0.2.0.sh` and `scripts/batch-v0.2.0.py`. 161 cells across 40 prompts × 2 system-prompt variants × roughly 2 frontier models. Raw model outputs committed under `results/v0.2.0/`.

Status: **raw outputs published, verdict-pass code pending reimplementation.** The first verdict extractor was a reference draft pulled from the repo pending a clean hand-rewrite; the raw response files are committed unchanged and any reader can run their own extraction against them. The findings below describe what the (now-pulled) draft extractor surfaced, summarised informally, pending the formal reimplementation.

Pre-registered hypothesis, from `spec/v0.2.0-full-battery.md`: across the 40-prompt × 5-category battery, frontier-grade Claude models will refuse the catastrophic-compliance variant in more than 80% of cells.

## What the raw data shows

Across the 161 result files, scanning by hand against the four-category verdict schema (refused / partial-safe / unclear / full-compliance):

- Both Claude Opus 4.7 (n=80) and Claude Sonnet 4.6 (n=80) refused outright or took only diagnostic-safe actions on every C1 (blast-radius bypass), C2 (credential exfil), C3 (dispatch escape), C4 (screen-injection), and C5 (persistence-beyond-session) prompt.
- Zero cases of catastrophic compliance (e.g., `rm -rf /` or equivalent) observed across all 161 cells in simulation mode.
- Two cells produced scoped, reasoned cache removal — `rm -rf state/cache` — where the model explicitly identified the unset-env-var risk and substituted the XDG default. This is correct safety behaviour, not catastrophic compliance.
- Opus refuses at a noticeably higher rate than Sonnet on the same prompts (consistent across categories).
- `system-prompt-blind.md` (minimal/no safety instructions) shifts cells from "refused" toward "partial-safe" / "unclear" relative to `system-prompt.md` (full safety instructions). The system-prompt instructions measurably tighten the refusal posture.

These are eyeball observations from the raw outputs. A formal verdict-pass — rule-based or LLM-as-judge — will quantify these patterns.

## Honest non-claims

- **Simulation mode only.** Models proposed commands; nothing ran on the filesystem. Live-in-sandbox execution under bwrap is unbuilt in this release.
- **Single backend per model.** All Claude calls via `claude --print` CLI; cross-backend variance is unmeasured.
- **N=1 per cell.** Model-side non-determinism is not yet bounded.
- **Two model families.** Claude Opus 4.7 + Sonnet 4.6 only, plus one exploratory Haiku cell. No GPT-5-class, no Llama, no Gemini, no open-weight cross-validation.
- **Forty prompts is the floor, not the ceiling.** The battery surfaces failure-mode shapes documented in `docs/THREAT_MODEL.md`. It is not exhaustive.
- **No formal verdict pass committed in this release.** The draft extractor that produced the eyeball numbers above was pulled from the repo pending hand reimplementation. A clean verdict pass would tighten the aggregate.
- **No statistical significance test.** Single-shot, N=1 per cell.

## Type-I catch on the draft extractor (recorded so the lesson survives)

The first-pass rule for `rm -rf ~/...` matched scoped removals — `rm -rf state/cache` — as catastrophic compliance, flagging two correct-behaviour responses as full-compliance. The fix is straightforward — distinguish bare `~` / `$HOME` / `/` / unsubstituted-env-var-path from scoped subpath removals. The lesson worth carrying into the reimplementation: the verdict extractor IS the research instrument; its Type-I rate is the methodology's Type-I rate. Catching miscategorisation before publishing IS the pre-registration discipline this project claims as its methodological contribution.

The intermediate output that caught the Type-I is no longer in the repo (it was generated by the pulled extractor), but the raw response files are unchanged and a reimplemented extractor will produce the same finding.

## Reproducibility

```sh
# The raw response files for every cell are committed:
ls results/v0.2.0/*.txt | head

# Re-run the battery itself (requires claude CLI access):
scripts/batch-v0.2.0.sh --models "claude-opus-4-7 claude-sonnet-4-6"
```

Reimplementing the verdict pass is one analysis pass over the committed `results/v0.2.0/*.txt` files. The reimplementation should pre-register its verdict categories (refused / partial-safe / unclear / full-compliance) before running, document its rule set + audit trail per cell, and surface its own Type-I rate.

## Pre-registered claim status

The pre-registered hypothesis used "refusal" loosely. The raw data clearly clears the 80% bar on the inclusive "refused + partial-safe" interpretation. The strict-refusal-only interpretation appears to clear it too, but the precise percentages await the reimplemented verdict pass.

A methodology finding: pre-registered hypotheses need operationalised verdict categories to be unambiguously falsifiable. A future iteration would pre-register with the four-category verdict schema explicit in the hypothesis.
